# T+13 上传模板错误排查

日期：2026-09-22。

依据用户提供的上传日志及 `D:\test\科目余额表T+13\解析辅助核算项目失败` 内的工作簿。仅记录 multipart 文件对应关系与业务响应，不保存请求中的认证信息。

## 本次请求

软件编号 2011（畅捷通 T+13.0），请求 `/api/ImportFromOther/ImportAsFromClientBatch`。

| 字段 | 实际上传文件 | 应选择文件 |
| --- | --- | --- |
| subject（科目数据） | 2023年发生额及余额表.xlsx | 科目(8).xlsx |
| trialbalance（科目余额表 / 期初表） | 科目(8).xlsx | 2023年发生额及余额表.xlsx |
| voucher（凭证数据） | 凭证导入导出(1).xlsx | 凭证导入导出(1).xlsx |

HTTP 200 的业务响应为 `code: 1`、`message: 导入任务创建失败：亲，请使用正确的导入模板导入！`、`data: ""`。该请求创建任务失败，不是日志目录名称所描述的辅助核算解析错误。

只读查看 XLSX 内部 XML 确认：余额表标题在 B2，科目编码/名称在第 7 行，第 1 行不存在；科目表第一行为科目编码、科目名称、余额方向、部门、个人、往来单位等字段。服务端 `ChanjetTPlus13ReadExcelHandle` 构造函数首先读取 subject 的第一个工作表，第一行为空即抛出与日志一致的模板错误。因此本次把余额表传入 subject 即会触发该前置检查。

## 客户端修复

原客户端仅接受 `Code/Message/Data`，实际响应为 `code/message/data`，导致真实业务错误被显示为“提交响应无法识别”。已让提交与查询结果支持 PascalCase / camelCase，继续校验任务编号及结果状态。

回归测试先复现两项失败，再验证小写业务错误可直接显示且不视为提交不确定、小写成功响应可取得任务并完成查询；同时保留原有大写格式覆盖。不自动交换文件，不修改原表格，不调用真实导账接口。

## 用户追加的附件选择调整

页面按科目表、余额表、凭证表排序，其他专用附件随后显示。选择科目表后，同目录文件名含“余额”“凭证”的可用候选自动填入相应空栏，不再要求文件名前缀相同；按用户后续要求，多个候选按文件名排序选第一个，不再展示候选下拉框。已选文件不覆盖，备份文件及不支持格式不参与匹配。

测试使用与用户样本相同的文件名组合（科目(8).xlsx、2023年发生额及余额表.xlsx、凭证导入导出(1).xlsx）验证自动填入与行顺序，并验证只有“余额”关键词且前缀不同的名称也可匹配。遵循用户要求，不生成新运行包。

最终验证：15 项测试通过、0 失败，附件顺序及自动填入截图已检查。测试构建隔离于 `.diagnostics/local-importer-host/Tests`，构建前后原 18 条 EXE/PDB 存在状态和哈希一致；最终保留原有 MSBuild PID 49680，未发现 PDB 服务残留。未替换用户启动程序。
